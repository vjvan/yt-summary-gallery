# 字幕語意校訂：完整話語視窗 + 句子錨點（v1 2026-09-07，v2 2026-09-08）

## 為什麼要有這一層

逐句翻譯的字幕（`/watch` 與影片庫的本機首輪）一次只看一句、沒有前後文，實測會出現：否定翻反（*There's not all these bottlenecks* → 「這些瓶頸你都得克服」）、量級放大（millions → 數以億計）、敘述變問句（*you're not afraid to say* → 「你敢不敢說」）、前後景顛倒（white on black → 白底黑字）、跨句斷詞（*take your job post* 當成職缺）。這些錯誤「流暢但錯」，不會被格式或字數檢查抓到。

`docs/translation-calibration-v18.md`（本機留存，不進 git）做過隔離評測：把舊譯文一起給模型二次校正，7B 與 gpt-4o-mini 都修不好否定與量級；只給原文與前後文的 source-only 模式才有改善方向。本層就是把那個結論做成產品流程。

## 做法

1. **話語視窗**（`lib/review/windows.ts`）：依句尾標點、停頓超過 1.5 秒、講者標籤、6 句／40 秒／600 字上限切窗，每窗帶前後各兩句當上下文。時間軸與 cue id 完全沿用原字幕。
2. **風險旗標**（`lib/review/risk-flags.ts`）：純規則比對原文與現行譯文，否定／量級／問句／前後景／數字五種是「對照後的落差」主導優先序；片段／比較／慣用語／代名詞只提醒需要上下文。實測三支影片高風險視窗約佔 15% 到 50%。
3. **重譯**（`lib/review/pipeline.ts`，v2 句子錨點）：只送原文、前後文與命中的字庫，**不送舊譯文**，也不送標題（7B 會把標題翻進去）。視窗原文先切成英文句子（`lib/review/sentences.ts`：句尾標點、`>>` 換人標記，縮寫與 J. Crew 不算句尾），模型依 `sentences[].n` 逐句回傳 `translations[]`（Ollama JSON schema 鎖句數，伺服器再驗 n 是否 1 到 N 各一次）。每句譯文只在「這句跨到的 cue」之間按字數比例分配（切點吸附標點，先找附近再放寬到一句份額內），所以就算模型多翻或少翻，漂移被關在一句之內，不會像 v1 整窗往後滑。只佔幾個字的句尾（`…early | on.`）併回相鄰 cue；`>>` 與講者標籤先剝再接回。句數對不上先換提示重試一次，仍不符才退回 v1 的整段比例切分並在備註標明「句界未對齊」。守門：保留詞、殘留英文、數字（10K 對 1 萬、50,000 對五萬、21 對二十一都算保留，「八十萬」不算 80 grand）、每句中英字數比（20 字以上的句子超過 0.65 提醒偏長、低於 0.14 提醒偏短，門檻取自既有 6,233 句的分布），可疑之處寫進 `notes`，格式錯就整窗丟棄。每窗一次呼叫、有檢查點，連續 5 窗失敗就停。
4. **候選與決定**（`lib/review/store.ts`、`service.ts`）：候選只存在 `subtitle_review_candidates`，人工逐句「採用／退回」；按「套用」才寫回 `segments_zh`／`transcript_zh` 並重寫 SRT／VTT，同一交易把每句「舊譯文 → 新譯文」記進 `subtitle_revisions`，「還原上一批」可整批退回。已燒錄的 MP4 不會自動重燒。
5. **只本機**：雲端模式直接拒絕；一次只跑一部影片；重啟不自動續跑，租約過期後手動繼續會沿用檢查點。

## 介面

影片詳情頁新增「語意校訂」分頁：統計（視窗／高風險／候選／已採用／已寫回）、每輪上限、「校訂高風險視窗」「校訂其餘視窗」「套用已採用」「還原上一批」；候選依視窗分組，每窗有「重新校訂本窗」（重譯這一窗，已採用但文字不同的句子回到候選），顯示原文／現行／候選三欄與備註，時間戳可跳轉播放器。

校準工具：`node --import tsx scripts/review-probe.ts <videoId> <windowKey,…|list> [--model m]` 對指定視窗跑一次重譯並印出逐句候選，不寫資料庫；用來重現回報的漂移句或比較模型。

API：`GET/POST/PATCH /api/summaries/{id}/subtitle-review`，細節見路由檔頭註解。請求走 `readWatchJson`（4KB 上限），逐句決定一次最多 500 句。

## 已知未做（backlog）

- 跨 worker 取消：取消只清掉租約與本 process 的 controller；另一個 worker 正在跑的模型呼叫要到下一個檢查點才會自己退出，這段期間可能同時有兩個推論在跑。需要跨 worker 的取消通知才能做到嚴格「一次一部」。
- 跨 process 的字幕寫入互斥（**2026-09-08 已做**）：整片重新翻譯開始前原子取得 `summaries.subtitle_write_token`（60 分鐘租約，同時要求影片沒有其他管線在跑），最終寫入以 token 加租約未過期為條件；語意校訂的套用／還原與外部譯文匯入在交易內看到佔用就回 409。**仍未涵蓋：影片庫的字幕續作（`lib/pipeline/local-youtube-library.ts`）還沒參與寫入權**，重新翻譯進行中若手動觸發續作，兩者最後會各自整份覆寫。最小修法是續作在第一個 await 前取得同一個 claim、finally 釋放，publish 的 UPDATE 加 token 與租約條件。
- 舊版的其餘互斥細節：
- 舊版的其餘互斥細節：套用／還原在交易內重讀字幕字串與工作狀態（status、subtitle_status、鎖、`lib/subtitle-writers.ts` 登記簿）做 CAS，重新翻譯與字幕續作也會登記；但登記簿只在同一個 Node process 有效，多 worker 部署需要持久化的字幕版本號。已寫回的句子若之後仍被整片重寫覆蓋，面板會顯示漂移句數並提供「重新套用」。
- 燒錄版本：套用字幕後，已燒錄的中文／雙語 MP4 不會被標成過期，再按燒錄會直接拿到舊檔。要做「字幕版本」綁定燒錄產物，套用後允許人工重燒。
- 對齊方式：句與句之間已用句子錨點對齊（v2）；一句跨多個 cue 時句內仍是字數比例加標點吸附，時間分配可能偏幾個字，不會偏一句。

## 邊界

- 候選是模型輸出，旗標與備註是規則提醒，都不是人工審校；採用前要自己看原文。
- 風險旗標會漏（沒有旗標不代表對）也會誤報（例如 A-not-A 問句偵測）；它只決定順序，不決定對錯。
- 沒有做「未見過的保留測試集」比較，不能宣稱整片正確率；要量化仍應另做盲測。
- 套用與還原在交易內重讀並以 `segments_zh` 原字串做 CAS；字幕續作、重新翻譯或另一個 worker 在中間改過字幕就整批不寫、回 409。字幕檔重寫失敗會記在 `export_error` 並在面板顯示「重新匯出字幕檔」。
- Chrome 擴充在 YouTube 原站用的是逐句快取（`data/watch*.db`），套用只改影片庫的 `segments_zh` 與 SRT，不回寫擴充快取。
